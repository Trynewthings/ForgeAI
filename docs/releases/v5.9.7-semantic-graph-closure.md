# v5.9.x Semantic Planning Progress Report

## Summary

The project has moved from a mostly template-and-heuristic compiler to a clearer semantic planning stack:

- authoring now maintains persistent semantic intent state
- compile consumes a shared `SemanticCore`
- graph planning is expressed as a typed evidence DAG
- graph structure authority stays in `compile + deterministic validator`
- `build` only decides bindings/materialization
- `runtime` only executes and reads semantics for explainability

The most recent milestone, `v5.9.7`, adds explicit graph-closure assessment so the system can distinguish:

- `graph_proposable`
- `graph_proposable_with_review`
- `clarification_required`

before a final bounded planning graph is proposed.

## What v5.9.x Completed

### v5.9 Repository analysis / architectural reporting

- introduced repository-analysis workflow support
- added evidence-first graph patterns for:
  - repository inventory
  - source structure extraction
  - relationship mapping
  - execution surface inspection
  - evidence bundling
  - report synthesis / render / delivery

### v5.9.1 Typed evidence planning

- capability semantics now include evidence in/out and semantic roles
- typed workflow locking prevents recognized graphs from collapsing back into generic 3-step skeletons

### v5.9.2 Repository source acquisition / checkout planning

- repository workflows now distinguish:
  - local workspace repositories
  - remote repository locators
  - unsupported / ambiguous repository sources
- acquisition is explicit and bounded

### v5.9.3 Unified capability semantics / planning graph integration

- planning graph is now a first-class typed DAG
- graph edges represent explicit evidence dependencies only
- reusable internal capabilities can participate in planning only when:
  - materialized
  - governance-valid
  - semantically defined

### v5.9.4 Semantic intent interpretation / graph proposal refactor

- compile moved away from keyword-first intent picking
- semantic interpretation became the primary graph-planning input
- graph proposals are now driven by semantic meaning, capability semantics, and bounded skeleton selection

### v5.9.5 Requirement semantic refinement / draft projection refactor

- requirement sessions now maintain persistent semantic refinement state
- draft JSON became a projection of semantic understanding rather than the primary source of truth

### v5.9.6 Shared semantic core between authoring and compile

- `SemanticCore` is now shared across authoring and compile
- compile no longer reinterprets intent from draft text when semantic state is complete

### v5.9.6.1 to v5.9.6.3 Semantic hardening / axis authority alignment

- authoring semantic refinement became LLM-first with deterministic hints + validation + fallback
- `SemanticCore` was split into cleaner axes such as:
  - `deliverable_form`
  - `analysis_frame`
  - `decision_posture`
  - `evidence_basis`
- `workflow_shape` became a real family/container constraint
- templates were explicitly demoted to packaging-only authority

### v5.9.7 Semantic graph closure / clarification integration

- graph closure is now an explicit compile-side decision
- clarification is triggered by graph-critical ambiguity
- review-needed is used for semantically plausible but partially grounded graphs
- compile explainability now surfaces why a graph was:
  - proposed
  - downgraded to review
  - blocked pending clarification

## Current Authority Model

The stack is now intentionally layered:

- `SemanticCore`: canonical intent understanding
- `BlueprintType`: top-level execution container
- `deliverable_contract`: derived compatibility label, not primary semantic truth
- typed workflow + evidence DAG: planning structure truth
- `template`: packaging and presentation defaults only
- `build`: realization/binding truth only
- `runtime`: execution truth only

## What Is Working Well Now

- semantically similar prompts are much more likely to converge to the same graph
- repository-analysis workflows are materially runnable through a bounded evidence chain
- compile is more honest about when clarification is required
- build no longer carries hidden graph-authority responsibilities
- runtime behavior remains bounded and auditable

## Known Remaining Gaps

- semantic coverage is still strongest in repository-analysis and report/briefing workflows
- not every capability has been fully backfilled with planning-quality semantics yet
- clarification wording is now graph-critical, but the product UX around clarification is still basic
- some generalized cross-domain workflows still depend on conservative fallback skeletons when no strong typed pattern exists

## Recommended Next Direction

The next high-value step is broader semantic/capability coverage rather than more rule expansion:

- expand semantic-capability alignment for cross-domain workflows
- improve graph-quality contracts for non-repository report/assessment cases
- strengthen product-facing clarification UX on top of the current structured closure model
