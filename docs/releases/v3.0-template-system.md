# v3.0 Template System

## Summary

v3.0 adds a minimal static template system to the compiler path without redesigning the compiler or weakening deterministic control.

The compiler now performs one extra deterministic step after legal family selection:

1. analyze requirement
2. recommend legal family
3. select a template within that family
4. generate the deterministic skeleton
5. apply template overlay only to existing slots
6. optionally pass template metadata as a hint into `llm_assisted` slot filling
7. validate and persist through the existing compiler flow

## What Changed

### Static template registry

A small family-scoped static registry is now defined under the compiler package.

Initial coverage is intentionally small and representative:

- `single_service.request_response`
- `workflow.monitoring_digest`
- `workflow.data_pipeline`
- `workflow.research_briefing`
- `multi_agent.review_escalation`

Each template is structured metadata, not a free-form prompt:

- `template_id`
- `name`
- `family`
- `description`
- `tags`
- `match_rules`
- `slot_hints`

### Deterministic template matching

Template matching is deterministic and family-scoped.

Inputs:

- normalized requirement
- already selected legal family

Matching uses transparent structured rules only:

- `domains`
- `recurrence_modes`
- `required_tools_any`
- `keywords_any`
- `human_review_required`

The matcher returns a machine-readable selection result including:

- `selected_template_id`
- `selected_template_name`
- `selected_family`
- `matched_candidates`
- `match_reasons`
- `selection_mode`
- `confidence`

### Template overlay

Template overlay is intentionally narrow and only applies after the deterministic skeleton already exists.

Allowed overlay targets:

- blueprint description
- existing step descriptions/purpose text
- existing artifact descriptions
- existing variable hints/defaults
- `template_tags_json`

Explicitly disallowed:

- adding/removing/reordering steps
- changing family
- altering the node graph
- creating arbitrary new artifacts
- inventing structural variables outside the existing skeleton

### LLM-assisted template hints

When `llm_assisted` slot filling is enabled, the selected template is passed as an extra prompt hint only.

This does not change the output contract:

- the filler still produces the same structured payload
- the filler still operates only on existing slots
- the model still cannot generate arbitrary workflow structure

### Trace and tags

Compiler trace now records template selection details in `decision_trace.template_selection`.

Blueprint drafts now carry template metadata via `template_tags_json`, including:

- `template_id`
- `template_name`
- `template_family`
- `template_source`

Compile history remains in the existing persistence model and carries the same template trace via the stored result payload.

## Fixed Checks

### Family authority remains independent

Verified behavior:

- family recommendation still runs before template selection
- template matching is scoped to the already selected family only
- templates do not have a code path to override or reopen family legality

Result:

- template selection is not a second family recommender

### Overlay remains slot-only

Verified behavior:

- template overlay only touches pre-existing deterministic payload slots
- unmapped template hints are dropped instead of expanding structure

Result:

- deterministic skeleton structure remains authoritative

### LLM filler authority did not expand

Verified behavior:

- template metadata is prompt input only
- filler output schema is unchanged
- filler still only fills bounded descriptive slots

Result:

- template hints improve context without widening model authority

### Trace, tags, and compile history are complete

Verified behavior:

- `decision_trace.template_selection` is present in compile results
- `blueprint.template_tags_json` contains template metadata
- compile history persists template selection through the existing result payload

Result:

- template usage is observable without introducing new storage layers

## Tests

Focused compiler coverage verifies:

- deterministic compile picks the expected template within the selected family
- template selection does not override family legality
- template hints reach `llm_assisted` filler while structure remains deterministic
- compile history payloads include template selection trace
- existing golden compiler validation still passes

## Deferred

Explicitly deferred in v3.0:

- template CRUD/admin APIs
- template database persistence
- template versioning/governance
- template UI/library surfaces
- LLM-generated templates
- cross-family template promotion logic
- template-first family selection
